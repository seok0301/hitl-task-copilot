# 최종 평가 실험 계획

이 문서는 개선 실험을 시작하기 전에 검증 세트(`app/seed/heldout_set.py`)와 함께 커밋한다.
가설, 지표, 판정 기준을 결과를 보기 전에 정해 두어, 결과에 맞춰 주장을 고르지 않았음을 남기기 위해서다.

## 세트 구분

- 개발 세트: `app/seed/eval_set.py`의 기본 세트와 어려운 세트. 알고리즘과 프롬프트를 고칠 때는 이 세트만 본다.
- 검증 세트: `app/seed/heldout_set.py`. 알고리즘을 고정한 뒤 마지막에 한 번 돌린다. 검증 세트 결과를 보고 알고리즘을 다시 고치면, 그 사실과 고치기 전 결과를 함께 보고한다.
- 사내 문서는 검증 세트를 만들기 전에 39개(회고 9개, 일반 문서 30개)로 늘렸다. 새 문서 중 일부에는 교훈과 규정이 있고, 일부는 교훈이 없는 검색 방해 문서다.

## 가설과 판정 기준

### H1. 수용 시간 제약은 LLM에 지시하는 것으로는 지켜지지 않고, 규칙으로는 보장된다

- 지표: 과부하 배정 건수(배정 후 기존 업무 + 가정 업무 + 이번 배정이 기간 수용 시간을 넘는 배정).
- 비교: 제안 방식, LLM 단독(수용 시간을 프롬프트로 지시), LLM 단독 + 규칙 후처리(LLM 순위에서 수용 시간을 넘는 후보를 건너뜀).
- 판정: 제안 방식과 규칙 후처리가 모든 반복에서 0건이고 LLM 단독이 0건보다 크면 지지한다.

### H2. 결정을 점수와 규칙에 맡겨도 정확도가 LLM 단독보다 크게 떨어지지 않는다

- 주 지표: Top-1(허용 담당자 포함). 보조 지표: Top-1(정답만), Top-3.
- 판정: 태스크 단위로 짝지은 차이(제안 방식 − LLM 단독)의 95% 부트스트랩 신뢰구간 하한이 −0.05보다 크면 "비열등"이라고 쓴다. 신뢰구간이 0을 포함하면 "차이가 유의하지 않다"고 쓰고, "더 정확하다"는 표현은 신뢰구간 하한이 0보다 클 때만 쓴다.
- 태스크 유형(normal, history, overload, accumulate)별 결과를 함께 보고한다.

### H3. 점수 기반 결정은 실행할 때마다 같은 결과를 낸다

- 지표: 반복 실행 사이에 Top-1 담당자가 모두 같은 태스크의 비율(반복 일치율).
- 판정: 제안 방식의 반복 일치율이 LLM 단독보다 높으면 지지한다. 제안 방식에서 남는 변동은 LLM 스킬 태그에서 오므로, 태그를 고정했을 때의 일치율(1.0이어야 함)도 함께 보고한다.

### H4. RAG는 회사 고유의 교훈이 필요한 태스크를 계획에 넣게 한다

- 조건: RAG 없음, 무관한 문서 무작위 주입(같은 개수, 대조군), RAG, 정답 문서 직접 제공(상한).
- 지표: 교훈 태스크 커버리지, 일반 태스크 커버리지. 판정은 LLM 심사와 키워드 판정 두 가지로 하고, 두 판정의 일치도(Cohen's kappa)를 보고한다.
- 판정: RAG − RAG 없음의 교훈 커버리지 차이에 대한 프로젝트 단위 부트스트랩 95% 신뢰구간이 0보다 크고, RAG가 무작위 주입보다 높으며, 일반 태스크 커버리지가 0.05 넘게 떨어지지 않으면 지지한다.

### H5. 검색 품질이 계획 품질을 좌우한다

- 지표: 교훈 태스크의 근거 문서가 검색 결과에 들어간 비율(Recall@k), 근거 문서를 찾았을 때와 못 찾았을 때의 교훈 커버리지.
- 검색 방식 변경은 개발 세트의 Recall@k로만 고른다.

### H6. 관리자 피드백이 계획 재생성에 반영된다

- 지표: 반영률(add는 요청한 태스크가 생김, remove는 요청한 태스크가 사라짐, limit는 태스크 수가 상한 이하), 보존률(요청과 무관한 이전 초안 태스크가 재생성 뒤에도 남은 비율).
- 비교: 피드백만 주고 다시 계획(기존 구현), 이전 초안과 피드백을 함께 주고 수정.

### H7. 보고 에이전트는 주어진 수치만 쓴다

- 지표: 경영진 브리핑에 나온 숫자 중 입력 지표에서 찾을 수 없는 숫자의 비율.
- 산출물 검토: 같은 태스크에 대해 완전한 산출물, 일부 빠진 산출물, 무관한 산출물을 주었을 때 충족도가 이 순서로 매겨지는 비율.

## 공통 조건

- 모델: gemma-4-26b(LiteLLM, temperature 0.2), 임베딩: paraphrase-multilingual-MiniLM-L12-v2.
- LLM이 끼는 조건은 5회 반복한다. 평가 DB는 개발 DB와 분리하고, 실행 전에 매번 seed로 초기화한다.
- 보고서의 수치는 `docs/report/results/`에 저장된 실행 결과만 쓴다.

## 개발 세트로 정한 것 (검증 세트를 돌리기 전에 고정)

검증 세트는 아래 결정을 모두 커밋한 뒤에 한 번 돌린다. 근거가 된 개발 세트 실행 결과는 `docs/report/results/exp-*-dev*.md`에 있다.

1. 문서 검색: 청크 단위 벡터 검색(chunk) 대신 문서 단위 글자 2-gram BM25(lexical)를 쓴다. 개발 세트에서 근거 문서 검색률이 0.47에서 0.89로 올랐다. 초안 태스크를 질의로 더하는 방식(draft)은 검색률이 비슷하고(0.91) 교훈 커버리지가 더 낮았으며(0.79 대 0.88) LLM 호출이 한 번 늘어서 쓰지 않는다. 임베딩 모델 교체(mpnet)는 검색률을 크게 바꾸지 못했다.
2. 계획 프롬프트: 참고 자료의 교훈·규정을 먼저 골라(lessons) 태스크로 옮기고, 태스크마다 근거(basis)를 남기게 했다. 정답 문서를 직접 주어도 교훈 커버리지가 0.50에 그쳐, 검색이 아니라 반영 단계가 병목이었기 때문이다. 바꾼 뒤 정답 문서 조건은 0.97, lexical 조건은 0.88이 되었다.
3. 후보 계층: 대체자를 "점수 1위와 같은 팀"이 아니라 "점수 1위와 같은 직함"에서 먼저 찾는다. 개발팀 안에 백엔드·프론트엔드·모바일·DevOps·팀장이 섞여 있어, 프론트엔드 적임자가 빠지면 백엔드 개발자나 팀장이 올라오는 오답이 있었다. 어려운 세트 Top-1이 0.920에서 0.952로 올랐다.
4. LLM 단독 비교군: 첫 번째 순위가 실제 배정이고, 앞서 배정한 태스크 시간도 더해 수용 시간을 넘기지 말라고 프롬프트에 명시했다. 5순위까지 받아 규칙 후처리 비교군(llm_only_capfilter)에도 쓴다.
5. 관리자 피드백 처리: LLM이 목록을 다시 쓰는 대신 편집 명령(remove, update, add)만 내고 코드가 적용한다(edit). 이전 초안을 주고 다시 쓰게 하면(rewrite) 빼라는 태스크 하나만 남기고 나머지를 지운 사례가 있었다. 개발 세트에서 edit는 반영률 1.000, 보존률 0.988이었다. 관리자 요청이 태스크 개수 규칙보다 우선한다는 문장도 넣었다.
6. 브리핑 숫자 판정: 입력 지표에서 바로 계산되는 값(완료 비율, 평균, 합계, "50%대" 같은 구간)은 근거가 있는 숫자로 본다. 개발 실행에서 걸러진 숫자를 사람이 확인해 보니 모두 이런 계산값이었다.

## 검증 세트 결과를 본 뒤 바꾼 것

실험 계획대로라면 검증 세트는 한 번만 돌린다. 1차 결과에서 아래 세 가지가 드러나 시스템을 바꿨고, 바꾼 뒤의 결과는 2차로 따로 보고한다. 1차 결과(`exp-*-final.md`)도 지우지 않고 함께 싣는다.

1. 담당자 추천 방식 교체. 1차에서 점수 방식(점수 + 수용 시간 규칙 + 후보 계층)은 Top-1 0.901로, 사전에 등록한 비교군인 "LLM 순위 + 규칙 후처리"(0.963)보다 낮았다(차이 −0.062, 95% 신뢰구간 [−0.116, −0.012]). 적임자가 과부하인 15개 태스크에서 차이가 가장 컸다(0.680 대 0.933). 점수 방식은 대체자를 같은 직함이나 같은 팀에서 기계적으로 찾다 보니, 성과 분석을 백엔드 개발자에게 넘기는 식으로 태스크의 뜻을 놓쳤다. 그래서 기본 방식을 LLM 순위 + 수용 시간 규칙으로 바꾸고, 점수 방식은 후보별 근거 표시와 LLM이 실패했을 때의 예비 경로로 남겼다. 바꾼 방식은 1차 때 이미 같은 검증 세트로 측정된 비교군과 같은 알고리즘이므로, 새로 맞춘 결과가 아니다. 시스템 코드로 다시 채점한 결과는 `exp-*-final3-matching.md`에 있다.
2. 계획을 두 단계로 바꿈. 1차에서 RAG를 쓰면 일반 태스크 커버리지가 0.083 떨어졌다(판정 기준 0.05 초과). 교훈 태스크가 태스크 자리를 차지해 기본 작업이 빠졌고, 관련 없는 검색 문서가 섞이면 과거 프로젝트 구성을 따라가는 경향도 있었다. 같은 현상이 개발 세트의 기본 세트에도 있었는데(0.817 → 0.767) 개발 단계에서 그 표를 놓쳤다. 개발 세트로 두 단계 방식(목표만 보고 기본 계획을 만든 뒤, 참고 자료의 교훈을 추가·수정 명령으로만 더함)을 시험해 확인한 뒤 바꿨다. 검증 세트 2차 결과는 `exp-*-final2.md`에 있다.
3. 삭제 요청 채점 기준 수정. 관리자 피드백 실험에서 "빼 달라"는 요청은 원래 "기준 작업이 계획에 포함되어 있는가"로 채점했는데, 이 심사는 다른 태스크 설명 속 언급도 포함으로 본다. 실제로 태스크가 지워진 사례도 실패로 집계되어, 삭제 요청은 "그 작업을 하는 별도 태스크가 남아 있는가"로 채점하도록 바꿨다. 세 재생성 방식에 같은 기준을 적용했다.
